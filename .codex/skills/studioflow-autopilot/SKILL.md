# StudioFlow Autopilot

Run only when invoked as `$studioflow-autopilot`. Treat the following request as the product objective. For long-running work, create a Codex Goal with concrete completion conditions derived from that request; mark it complete only after the requested behavior, relevant validation, review, and repairs are finished. If Goals are unavailable, report that limitation instead of inventing a substitute.

Follow the repository's `AGENTS.md` for source-of-truth, context routing, permissions, and validation. Inspect the current implementation before choosing an approach. Classify the task internally as micro/local, normal feature, intentional visual redesign, or complex/cross-domain/database. Read only relevant architecture references and existing repo skills when they materially help; do not load Graphify by default. Preserve StudioFlow's established product and visual language unless the request changes it.

- **Micro/local:** Implement directly. Do not spawn investigation or writer agents unless clearly useful.
- **Normal/complex:** Keep the main thread as the primary implementation writer. Use Luna High explorers selectively; use `code_mapper` when tracing a multi-file flow. Run parallel agents only for genuinely independent investigation, and pass narrow questions instead of repeating large repository context. Delegate implementation only when isolated ownership materially helps. Keep implementation decisions in the main thread.
- **Intentional visual redesign or new visual surface:** First ask `design_director` (GPT-6 Astra High) for one design contract grounded in the rendered surface, available screenshots, current implementation, and sibling UI. Give that contract to the main agent before implementation. The main agent implements it, then asks `visual_reviewer` (GPT-6 Astra High) to inspect the rendered result at relevant desktop, notebook, and mobile widths. Fix confirmed visual findings; a fundamentally weak composition calls for redesign, not only spacing tweaks. Then run the Sol code review and focused validation below before completing the Goal. This sequence does not apply to small UI fixes.

For the design phase, ask `design_director` to use one relevant design skill, never an automatic stack of broad skills: `frontend-design` by default for substantial visual redesigns or new frontend surfaces; `gpt-taste` only when the task specifically calls for stronger art direction or distinctive visual exploration, instead of `frontend-design`; `ui-ux-pro-max` for UX flows, interaction structure, information architecture, or usability decisions; `design-system` for tokens, theme architecture, or reusable component/system work. Use `impeccable` only for final whole-feature polish when a substantial completed feature materially benefits. Use GSAP skills only for genuinely motion-heavy work. An ordinary project-summary redesign uses `design_director` with `frontend-design`.

In the design contract and implementation, preserving information does not require preserving its layout. Avoid generic dashboard grids, rows of equal-weight metadata, arbitrary max-width containers, and filling space for its own sake. Compact must remain comfortable; whitespace should establish hierarchy. Add no animation merely for decoration, but use subtle transitions when they improve polish.

After implementation and any visual repairs, ask the `studioflow_reviewer` agent (GPT-6 Sol High) to use `$studioflow-review` on the actual resulting diff against the original request. Pass the request, diff scope, and any validation results; have the reviewer inspect the files rather than pasting large repository context. Use this same reviewer for DB, Finance, RLS, historical-integrity, and other high-risk changes. Fix confirmed findings, then run focused validation matched to risk: TypeScript when relevant for UI, focused tests for local logic, and invariant/RLS checks for database changes. Broaden regression or build checks only for a concrete integration risk. Report a failed optional visual check as a caveat; keep the Goal open when a required acceptance check fails. An intermediate completion is not the finish line.

Ask the user only for a material unresolved product choice, approval for a destructive/remote/production action, or a blocker the repository cannot resolve. Respect normal sandbox and approval boundaries. End with a compact account of the change, checks, review outcome, and remaining caveats.
